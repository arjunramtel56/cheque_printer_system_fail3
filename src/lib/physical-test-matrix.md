# Physical Print Protocol — per cheque template

> **The rule this document exists to enforce:** a cheque template is *not*
> implemented because it looks right in the browser. Browser preview and
> physical output are recorded in **separate columns**, and a template only
> reaches `physically-calibrated` when a real sheet has been measured.

| Status | Meaning | Evidence required |
|--------|---------|-------------------|
| `unverified` | Geometry is placeholder. Not selectable for printing. | Sample cheque photograph + coordinate read-off |
| `browser-verified` | Geometry, page box and field rectangles confirmed in the browser print preview. | `tests/preview-print-parity.test.mjs`, `tests/geometry-matrix.test.mjs` |
| `physically-calibrated` | Ink lands within ±0.5 mm of the expected position on real cheque stock. | Completed record sheet below, measured with a ruler |

Current state of the catalogue: **5 templates, 1 browser-verified
(`siddhartha`), 0 physically-calibrated.** Everything below is the *expected*
half of the record sheet; the *actual* columns are empty on purpose.

---

## 1. How the expected numbers are produced

Every millimetre in this document is generated by `src/lib/sheetLayout.ts`, which is
also what the screen preview and the printed page both render. There is exactly
one layout pipeline, scaled by a constant for the screen, so a number that is
wrong here is wrong on paper too — and a number that is right here lands where
the preview showed it.

```
template (src/data/)          cheque size (src/lib/sizes.ts)     paper (src/lib/sizes.ts)
        \                        |                              /
         \                       v                             /
          +--> resolveCalibratedGeometry(template, mode, cal) --+
                          |
                          v
                 computeSheetLayout(...)  -->  mm rectangles
                          |
              +-----------+-----------+
              |                       |
        ChequeSheet (screen)    ChequeSheet (print)   <- same component
```

To regenerate the expected tables after any geometry change:

```bash
npx tsx .freebuff/geometry-report.mts
```

Never hand-edit the expected coordinates. If they no longer match the code, the
code moved and the record sheets are stale.

The four clone-geometry templates exist so the *pipeline* can be exercised with

coordinates are entered from a sample cheque. Cloning geometry is the specific
failure mode this protocol is designed to catch: four banks that "work" in the
browser and print in the wrong place on paper.

**Adding a bank:** photograph its cheque face-down flat, measure total width and
height in mm, register the size in `src/lib/sizes.ts`, enter the field rectangles in
`src/data/templates.ts`, flip `verification.status` to `browser-verified`, then run
this record sheet.

## 4. MICR / security band — reserved, never printed

Every template declares the bottom band of the cheque as a **reserved safe
zone** (`safeZones[].id === "micr"`). It is rendered on screen as a hatched
danger area and is excluded from printing entirely:

- `isPrintableKind()` never returns true for a safe zone.
- A field that overlaps a reserved zone fails `validateBankTemplate`, so the
  template is blocked at load rather than discovered on a printed cheque.
- The stated rule for the field editor: **nothing may be positioned inside the
  reserved band.** Printing over the MICR line makes the cheque unredeemable.

For `siddhartha` the reserved band is Y = 81.90 … 88.90 mm (the bottom 7 mm).

## 5. Record sheet — copy one block per template

Fill this in with a ruler in hand. Expected values come from section 3; actual
values are measured from the paper edge to the ink edge.

```
Template: ____________________   Size: ______ × ______ mm   Orientation: ______
Print mode: __________________   Printer: ________________  Date: _____________
Paper:  [ ] cheque stock   [ ] A4 carrier     Scaling: Actual Size (100%)
[ ] Margins: minimum/none    [ ] Borderless off    Starting calibration: X=0.00  Y=0.00

| Field          | Expected X | Actual X | ΔX  | Expected Y | Actual Y | ΔY  |
|----------------|------------|----------|-----|------------|----------|-----|
| Date           |            |          |     |            |          |     |
| Payee name     |            |          |     |            |          |     |
| Words line 1   |            |          |     |            |          |     |
| Numeric amount |            |          |     |            |          |     |
| A/C PAYEE      |            |          |     |            |          |     |
| MICR band edge |   (must stay blank — if any ink appears here, STOP)         |

Correction = Expected − Actual
Final calibration: X = ________ mm    Y = ________ mm
Second print deviation: ΔX = ______ mm   ΔY = ______ mm     [ ] ≤ 0.5 mm  → PASS
```

Record one block per (template × print mode). A template is only
`physically-calibrated` when all four modes pass. Calibration is stored per
template **and** per mode, so passing Direct Feed says nothing about A4.

## 6. Calibration independence

| Action | Direct Feed calibration | A4 calibration |
|--------|------------------------|----------------|
| Direct Feed → A4 Carrier | preserved | preserved |
| A4 Carrier → Direct Feed | preserved | preserved |
| Edit either mode's X/Y | untouched | untouched |
| Change template | its own set | its own set |

Each (template, mode) pair owns its own calibration record. X moves the content
horizontally only, Y vertically only, and **neither changes the cheque's
physical size** — asserted in `tests/geometry-matrix.test.mjs`.

## 7. Validation gates that block a bad print

| Check | Enforced by | On failure |
|-------|-------------|------------|
| Cheque size not a positive mm value | `validateSize` | Size rejected |
| Decimal degrees of freedom on mm values | `isValidSizeValue` | Size rejected |
| Template size ≠ declared orientation | `orientationMatchesSize` | Template rejected |
| Field outside cheque bounds | `validateBankTemplate` | Template rejected at load |
| Field inside a reserved safe zone | `validateBankTemplate` | Template rejected at load |
| NaN / Infinity calibration | `clampCalibration` | → 0 |
| Calibration beyond ±25 mm | `validateCalibratedBounds` | Print blocked |
| Cheque pushed off the paper by calibration | `validateCalibratedBounds` | Print blocked |
| Bank disabled or template unverified | `getSelectableBanks` / route guard | Not selectable |

## 8. Instructions

1. Open the template's route: `/banks/<bank>/cheque/<template>`.
2. Select the print mode recorded on the sheet.
3. Enter a valid date, payee, amount and (optionally) words.
4. Set calibration to X = 0.00, Y = 0.00 — a known starting point is the whole
   point of the exercise.
5. **Print Cheque** → in the browser dialog:
   - Scaling **Actual Size (100 %)** — never "Fit to page".
   - Margins minimum/none.
   - Cheque feeder for Direct Feed, flat tray for A4 carrier.
6. Measure each printed field from the paper edge with a ruler.
7. Compute the correction, apply it in the calibration panel, re-print.
8. Repeat until every Δ ≤ 0.5 mm, then record the final calibration here and
   mark the template `physically-calibrated` via the admin workbench.
9. Run the MICR check: the reserved band must be **blank ink-free**.
10. Do this on at least two different physical printers before calling a
    template production-ready — calibration is per printer, and the app ships
    the operator's calibration with the template, not the factory's.

> Different paper sources on the same printer (rear tray vs. manual feed) often
> have different offsets. If so, keep one calibration record per paper source.
> The ±25 mm range exists to absorb exactly this.
